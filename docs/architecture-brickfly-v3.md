## 0. 文档定位
本文件统合本项目全部讨论成果，作为架构层面的**设计与论证文档**。它回答"为什么这样设计、各部分如何协作、边界在哪"；配套的 `blender-rules.md` 是它的执行契约（"具体怎么做"）。两者配套使用：本文档给设计者看，rules 给模型看。
**平台铁律**：本架构只在 Zcode + Blender + blender-mcp + API 大模型这套组合上成立。所有超出此平台的能力（微调、多 Agent 框架、端到端生成）均不在主干内，见第 7 章。

## 1. 路线选择：为什么是力大砖飞
### 1.1 两种 3D AI 的本质区别
| | 生成式路线 | 力大砖飞路线（本架构） |
|---|---|---|
| 产出 | 一个静态 mesh 资产 | 可执行代码 + 可编辑场景 |
| 尺寸精度 | 不可控，只能"像" | 精确，说 0.007 就是 0.007 |
| 拓扑 | 黑盒，不可控 | 代码即拓扑，面数可控 |
| 可修改性 | 重生成 | 改参数重跑，或直接进 Blender 手改 |
| 智能来源 | 模型底座（权重） | 推理 + 反馈 + 记忆（外围） |
### 1.2 能力边界（本架构的诚实声明）
- **碾压区**：硬表面/机械、参数化/程序化资产、场景组装、材质灯光渲染
- **勉强区**：基础有机形体（多轮迭代可出）
- **放弃区**：雕刻级细节——架构在此预留侧门（第 6 章），但主干不解决
### 1.3 平台现实
API 模式下权重不可触，**模型本身永远"就是这个智商"**。因此本架构的全部设计空间在于：喂给模型什么（上下文）、模型记得什么（记忆）、模型被要求怎么做（协议）、模型一次任务允许烧多少算力（推理时计算）。这四条正好对应后文四个机制群。

## 2. 平台约束与设计公理
### 2.1 平台四件套的角色
```
ZCode      = 调度舱（会话容器 + MCP 宿主）
GLM (API)  = 大脑（无状态、可深度思考、无权重访问权）
blender-mcp = 传送带（execute_code / get_scene_info / viewport 截图）
Blender    = 车间（场景唯一真值所在地）
```
### 2.2 五条硬约束 → 五条设计公理
| 约束 | 推出的公理 |
|---|---|
| C1 权重不可触 | 一切优化压到外围：上下文工程 + 记忆 + 协议 + 推理时算力 |
| C2 单会话单模型 | "规划/编码/批评"多角色用**协议阶段切换**模拟，不引入多 Agent 框架 |
| C3 token 预算有限 | 上下文是稀缺资源：反馈分级、记忆只存指针、中间产物主动丢弃 |
| C4 Blender API 有版本断层 | 防幻觉必须是系统性工程（契约禁令 + 跨版本 helper 双保险） |
| C5 模型无状态、场景在 Blender 侧 | **状态所有权归 Blender，模型只能通过 report JSON 投影感知** |
C5 是全架构最重要的一条公理，单独展开见 M3。

## 3. 总体架构
### 3.1 架构总图
```
┌──────────────────────────────────────────────────────────┐
│ L1 调度层  ZCode 会话中的 GLM（API）                       │
│   角色随协议阶段切换：规划者 / 编码者 / 批评者 / 归档员      │
│   深度思考按配额使用（M12）                                │
├──────────────────────────────────────────────────────────┤
│ L2 契约层  blender-rules.md                               │
│   行为协议 + 硬性禁令 + 代码骨架 + 反馈节奏 + 记忆兼容铁律  │
├────────────────────────┬─────────────────────────────────┤
│ L3a 语义记忆（平台侧）  │ L3b 工作资产（skills/ 文件系统）   │
│  · 教训 / 偏好          │  · fragments/*.py  代码积木       │
│  · 组件指针（仅指针）   │  · nodes/*.blend   参数化节点组   │
│  · 读写方式本地自适应   │  · api-reference.md 速查         │
├────────────────────────┴─────────────────────────────────┤
│ L4 执行层  blender-mcp → Blender                          │
│   execute_code / get_scene_info / viewport 截图           │
│   bpy 渲染管线（EEVEE 快渲 / Cycles 精渲）                │
└──────────────────────────────────────────────────────────┘
```
### 3.2 一次任务的状态机
```
IDLE
 → 检索     查 L3a 教训 + 组件指针（命中→短路复用，未命中→新任务）
 → 规划     方案层输出（复杂任务触发 M6 多路径搜索）
 → 执行环   ┌ 生成代码（骨架模板）
            │ 执行（幂等保证）
            │ report JSON 回报（状态投影）
            │ 视觉反馈（按 M5 分级触发）
            │ 诊断 + 修正（Reflexion 引用教训编号）
            └── 循环至本阶段达标
 → checkpoint ×4（几何 → 材质 → 构图 → 灯光，阶段隔离）
 → 验收     用户确认
 → 归档     教训入 L3a，积木入 L3b，索引指针更新
 → IDLE
```
关键性质：**执行环内任何一轮失败只回滚当前子目标；阶段 checkpoint 之间互相隔离，下游只引用上游 report JSON，永不凭模型记忆假设场景。**

## 4. 机制详解
### M1 方案先行与代码骨架
**机制**：建模任务先出方案（物体清单、基元、修改器、参数），用户确认后进代码轮；所有代码遵守统一骨架（参数区→幂等清理→helper→建模→report）。
**动机**：方案层挑错成本是代码层的一成以下；骨架统一让幂等、回报、验证成为结构性保证而非自觉。
**依据**：SEIG 类分阶段执行的通用结论——结构与协议带来的稳定性远超模型自觉。
### M2 幂等执行
**机制**：每段代码以 `PREFIX` 为前缀，开头清理同前缀旧物体，保证跑十遍场景状态一致。
**动机**：多路径搜索（M6）要求同场景反复重建互不污染；迭代失败重跑不留残渣。
**失效边界**：前缀命名冲突；对非本架构管理的物体误删——契约限定只清理 `PREFIX_*`。
### M3 结构化回报与状态所有权
**机制**：每段代码结尾 `print(json.dumps(report))`，输出物体名、位置、尺寸、三角面数；下一轮推理**必须引用该 JSON**，禁止凭记忆描述场景。
**动机**：这是 C5 公理的落地。模型没有眼睛，场景的真值只在 Blender 里；report 是场景向模型世界的**只读投影**，谁持有投影谁就能正确决策。
**失效边界**：report 字段不足以诊断的问题（穿模、比例观感）→ 交给 M5 视觉反馈补盲。
### M4 四阶段隔离流水线
**机制**：复杂任务强制拆四个 stage：**几何 → 材质 → 构图 → 灯光**，每阶段一个视觉 checkpoint，阶段失败只回滚本阶段。
**依据**：SEIG（Staged Executable Inverse Graphics, arXiv 2606.02580）实验结论：分阶段逐步精修的重建保真度显著优于一次性生成，且无需专用基座、无需可微渲染——通用 VLM + 可执行代码空间即可。
**边界**：简单任务（单物体、无材质要求）可跳过阶段直接走执行环。
### M5 三级视觉反馈
**机制**：按时机分级取"看"的成本：
| 级别 | 手段 | 成本 | 时机 |
|---|---|---|---|
| 眼快扫 | blender-mcp `get_viewport_screenshot` | 毫秒 | 每轮小步迭代 |
| 快渲 | bpy + EEVEE，16 采样 | 秒 | 阶段 checkpoint |
| 精渲 | bpy + Cycles，128 采样 | 分钟 | 里程碑/用户验收 |
看图后先输出三句视觉诊断 JSON（比例/材质/穿模）再写下一轮代码。
**动机**：纯代码路径的致命盲区是"执行成功 ≠ 建得对"。DD3M 实测：无视觉反馈时顶级模型也只能出基元拼凑体。
**纪律**：视口须切材质预览模式（截图前置代码）；中间轮截图在阶段收尾后丢弃引用——这是 M11 上下文预算的一部分。
### M6 多路径搜索（测试时计算）
**机制**：复杂任务（判定：超 2 阶段 / 有机形体 / 用户要求"好看"）触发——一轮生成 **3 套实质不同的方案**（不同基元策略/修改器组合/拓扑思路），并行执行（幂等保证互不污染），各截图一张，GLM 以批评者角色对比诊断择优，落选方案中可用代码段归档 fragments/。
**依据**：GIF-MCTS（NeurIPS 2024）与 LATS 共同验证：单次代码生成失败率高，搜索树 + 环境反馈择优可大幅提升成功率。这是"测试时计算扩展"的工程化——C1 约束下，算力换正确率是唯一可开的挂。
**边界**：成本是 3 倍执行 + 3 张截图 token；仅复杂任务触发，简单任务单路径直行。
### M7 API 防幻觉体系
**机制**：三层防线——
1. **契约禁令**（rules.md）：交互式 op（`loopcut_slide`）、UI 依赖 op（`screen.*`/`view3d.*`）、已废弃参数（`do_unlink`、`use_auto_smooth`）、3.x context override 写法，全部禁用并给替代写法；
2. **跨版本 helper**：socket 赋值一律候选名列表 + `.get()` 探测（`set_input(bsdf, ["Specular","Specular IOR Level"], v)`），对抗 4.0/5.0 大规模改名；
3. **诚实原则**：不确定的 API 输出 `todo` 标记交人工确认，禁止编造。
**动机**：Blender API 版本断层 + 模型训练数据滞后 = API 幻觉是**结构性风险**而非偶发失误，必须系统性设防。
### M8 Reflexion 教训记忆
**机制**：执行失败后，模型输出三段式归因（错误现象/根因/规避法），写入 L3a 持久记忆；下一轮代码注释顶部必须引用相关教训编号。
**依据**：Reflexion（NeurIPS 2023）：语言化自我反思存入 episodic 记忆后重试，决策质量显著提升，尤其适用于"信息都在但模型没正确综合"的场景——bpy 建模正是典型。
**边界**：教训只在失败发生时写，防止记忆库被平庸信息灌水。
### M9 组件复用阶梯
**机制**：写建模逻辑前按固定优先级找现成方案：
1. `skills/nodes/` 参数化节点组（调参数即用）
2. `skills/fragments/` 代码积木（import 改参数）
3. L3a 记忆中的组件指针 → 按 path 取文件
4. 全无 → 从基元写起，完成后归档
**动机**：对抗"每次从零开始的重考生"模式。运行足够久后，常规任务退化为"查索引→调积木→改参数"，推理预算全部留给真正的新问题。
**依据**：DD3M 的检索骨干设计；程序化路线的长期主义判断（Datameister："3D 生成的未来是程序化的"）。
### M10 记忆兼容与单一事实来源
**机制**：本架构自带记忆设计与使用者已有记忆库共存时的职责切分：
| 信息类型 | 唯一权威家 |
|---|---|
| 教训、偏好（语义知识） | 使用者已有记忆库（L3a） |
| 代码积木、节点组、API 速查 | `skills/`（L3b） |
| 组件索引 | L3a，但**只存指针**（名+路径+一句话用途） |
三条铁律：**单一事实来源**（每类信息只有一个家）、**禁止双写**（双写=未来必有一份过期）、**指针必须验证**（记忆说有某积木，执行前必须确认文件真实存在，验证失败按"无此积木"处理并修正记忆——这是防腐烂保险）。
**动机**：记忆双轨制是同类架构最常见翻车点；本地记忆环境形态不定（内置/文件/MCP），故 L3a 读写方式由模型**本地自适应判断**，契约只约定原则不约定工具。
### M11 上下文预算管理
**机制**：长会话的隐形杀手是 context rot——工具描述+多轮截图+JSON 回报堆积几万 token 后模型系统性变笨。对策写入契约：反馈分级触发（M5）、阶段收尾丢弃中间截图引用、blender-mcp 之外的工具按需挂载（建模期不挂其他 MCP）、report JSON 字段精简（round 到小数点后 4 位）。
**依据**：上下文工程研究（Anthropic 指南等）一致结论：token 越多性能越差，长上下文≠会用长上下文。
### M12 深度思考配额
**机制**：深度思考模式只在**方案层与诊断层**开（真正需要推理密度的地方），**写代码层关**（代码生成是执行密集型，长思考边际收益低还拖速度）。
**动机**：C3 约束下思考算力也是预算，按环节分配而非全程拉满。

## 5. 失败模式与对策总表
| 失败模式 | 症状 | 对策 | 归属机制 |
|---|---|---|---|

| 记忆腐烂 | 指针指向已删文件 | 指针验证 | M10 |
| 双写冲突 | 两份记忆各执一词 | 单一事实来源 | M10 |
| 同错复发 | 同一坑摔两次 | 教训编号引用 | M8 |

| 视觉盲飞 | 代码成功但建歪了 | 三级视觉反馈 | M5 |

## 6. 扩展通道（预留，非主干）
**有机形体侧门**：雕刻级细节（角色面部、生物肌肉）是砖飞放弃区。架构预留的接口是——由外部生成模型（混元/Rodin/Meshy/Tripo 等，均具备 MCP 通道）出**粗胚资产**，再由本架构主干做导入、精修、摆位、材质。设计原则：**侧门必须主动选用，而非被架构绑架默认启用**。当前平台（zcode+blender+mcp+api）不含生成模型接入，此通道处于关闭状态，主干完全不依赖它。
**Geometry Nodes 作为程序化中间表示**：L3b 的 `nodes/` 目录即为此预留。节点组是比代码积木更高一层的复用形态——参数面板化，非程序员可直接调参。其地位随资产积累自然升级，无需架构变更。

## 7. 刻意排除项及理由
| 排除项 | 理由 |
|---|---|
| RLVR / 微调 | API 模式无权重访问权，物理不可能 |
| 多 Agent 框架 | ZCode 单会话下用协议阶段切换角色更便宜且不丢上下文 |
| 端到端生成为主干 | 尺寸不可控、拓扑黑盒，违背力大砖飞根本收益 |
| 大上下文全量堆喂 | context rot 风险，见 M11 |

## 9. 演进逻辑（触发条件式，非时间表）
本架构按**信号驱动**演进，出现以下信号时才启动对应升级，不预设日程：
- **信号：同类错误第三次出现** → M8 条款强化，该教训升级为契约禁令候选
- **信号：常规任务索引命中率过半** → 组件库进入收获期，重点投入 nodes/ 节点组化
- **信号：复杂任务择优后仍频繁失败** → M6 搜索宽度从 3 提到 5，或对该类任务启用有机侧门评估
- **信号：会话频繁触顶溢出** → M11 加码（report 字段再精简、checkpoint 后强制压缩历史）
- **信号：Blender 大版本升级** → M7 禁令清单与 helper 候选名全量复审
- **信号：某类任务流程完全稳定** → 该流程固化为新契约条款，从"协议"降格为"肌肉记忆"

**与 rules.md 的关系**：本文档是设计论证（why），`blender-rules.md` 是执行契约（how）。架构变更时先改本文档的对应章节，再同步契约条款——文档是契约的上游。
**样例轨迹**（M4 螺丝任务，验证协议可行性）：方案层输出六角头+螺杆+倒角的参数计划 → 用户砍掉螺旋细节 → 骨架代码执行 → report 显示尺寸精确到 0.0001、面数 124 → 模型自查发现 bevel 全选误伤底部 → 修正段 → 达标。全程体现 M1/M2/M3 三个机制的协作，也是"尺寸精确+实时可控+自我修正"三优势的最小证明。
